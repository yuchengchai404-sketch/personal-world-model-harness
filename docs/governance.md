# Governance

## Ownership model

| 对象 | AI 权限 | 用户权限 |
|---|---|---|
| Source / Note | 可读取、解释、建议写入 | 可修改、确认或否定 |
| Candidate / Testing Insight | 可提出、挑战、补证据 | 可确认归属、调整状态 |
| Candidate Model | 可建议和测试 | 决定是否继续验证 |
| Active Model | 不得无感修改 | 最终批准、修订或撤回 |
| CORE / USER | 只能提出实质变更建议 | 批准后方可修改 |
| STATE | 完成任务后可更新 | 可随时纠正 |

## Attribution discipline

输出与资产应区分：

- 用户原始表达；
- 来源中的事实或解释；
- AI 的推断、挑战或竞争模型；
- 用户确认后的个人判断。

AI 可以制造认知增量，但不能制造归属错觉。

## Independent challenge

高质量反馈至少检查：

1. 准确部分及依据；
2. 事实、解释、价值判断、因果与相关；
3. 隐藏假设；
4. 尚未纳入的新信息；
5. 反例与失效边界；
6. 竞争解释；
7. 可证伪或可支持的现实检验。

## Analogy validation

当类比承担解释或推理作用时，执行三步鉴：

1. 结构相似性；
2. 属性相似性；
3. 失效边界。

类比用于生成理解和假设，不用于替代证据。

## Approval boundary

以下动作需要明确批准：

- 实质修改 CORE、USER 或 Active Model；
- 删除或覆盖原始 Source；
- 大规模移动、重命名或归档；
- 对外发布真实 Vault 或连接外部服务。

## Anti-overengineering

出现以下现象时，应优先简化：

- 维护 Properties / Links / Status 频繁打断思考；
- 为使用 Multi-Agent 而使用 Multi-Agent；
- 为自动化而自动化；
- 整理系统的时间接近真实学习和应用；
- 系统依赖大量人工维护才能保持表面整洁。
